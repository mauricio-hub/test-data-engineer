# Operación y evidencia de S01

S01 prepara entorno, permisos y auditoría. No carga datos ni crea tablas de negocio. No se ha autorizado S02.

## Ejecución desde cero

Requisitos externos: GNU Make, Python 3.11 o superior con venv/pip y Docker Compose v2 con motor Linux activo. Se necesita red para instalar paquetes y descargar imágenes. No se instalan ni reconfiguran herramientas del sistema automáticamente.

1. `make setup`: crea `.venv/`, instala `requirements.txt` y genera configuración local.
2. `make up`: espera salud de PostgreSQL/Redpanda, comprueba contraseña del volumen, prepara SQL y comprueba conexión TCP de cada rol.
3. `make test`: ejecuta pruebas unitarias y conexiones/permisos reales; falla si PostgreSQL no está accesible.
4. `make down`: detiene los servicios y conserva volúmenes para reintentos.

En Windows, si pyenv no selecciona Python, usar `make PYTHON="ruta/al/python.exe" setup`. Sin GNU Make pueden ejecutarse los comandos equivalentes de las recetas, pero eso no certifica el contrato del evaluador.

`make run`, `make stream` y `make clean` devuelven error explícito. El verificador suministrado no se modifica: todavía fallará por objetos de negocio y datos del candidato pendientes.

## Credenciales y permisos

- `.local/` y el manifiesto generado se excluyen de Git. Excluir `.local/` del ZIP: no copiar credenciales de una instalación a otra; setup genera las locales del evaluador. El ZIP sí requiere `entrega.yaml`, que se actualizará al preparar el entorno. `entrega.example.yaml` conserva la plantilla sin secretos.
- Cuatro contraseñas aleatorias independientes de 256 bits. Repetir setup las conserva; no rota automáticamente sobre volúmenes existentes. Si se pierde el estado, restaurarlo o preparar un entorno nuevo explícitamente; no borrar volúmenes por defecto.
- El manifiesto generado usa JSON, formato válido para el lector YAML suministrado. Preserva los datos humanos del candidato; los TODO de objetos de negocio son intencionales.
- La aplicación usará `.local/ingesta.json`, sin cuentas administrativas. El operador local controla los archivos y el superusuario: esto no crea aislamiento contra ese operador.
- En POSIX se aplican permisos 0700 al directorio y 0600 a archivos. En Windows se heredan las ACL del directorio; no se afirma equivalencia con permisos POSIX.
- No se genera ni guarda llave PII. No hay implementación de cifrado en S01.
- Propietario `bia_owner` sin login. Sin permisos públicos de conexión, creación de esquemas o tablas temporales para roles operativos. Los roles no pertenecen al propietario.
- `ingesta` solo ejecuta `audit.record_run`; `auditor` lee `audit.runs`. El actor se toma de la conexión, y operación/resultado son valores acotados. Ninguno modifica, borra, trunca o altera auditoría.
- No existen aún permisos de negocio ni vista definitiva. Las pruebas crean y eliminan objetos sintéticos únicos para comprobar lectura de vista y UPDATE autorizado, manteniendo PII inaccesible.
- Puertos ligados a 127.0.0.1; Kafka local sin autenticación/TLS, accesible a procesos locales. No es una configuración de producción. MinIO se retiró por no ser necesario en este alcance.

## Dependencias revisadas (T20)

- Se retiraron requests, urllib3 y Jinja2: ninguna herramienta actual los necesita. Se retiró pandas: S01 no lo usa; no se asume que será necesario después.
- Se conserva PyYAML 6.0.3 para el manifiesto y verificador, y psycopg2-binary 2.9.13 para el verificador y futura conexión del pipeline. Son versiones explícitas publicadas en [PyPI/PyYAML](https://pypi.org/project/PyYAML/6.0.3/) y [PyPI/psycopg2-binary](https://pypi.org/project/psycopg2-binary/2.9.13/). Se usan consultas YAML seguras; psycopg2 binario evita compilación para evaluación local.
- El productor necesita kafka-python; su incorporación corresponde a S05, no se declara operativo ahora.
- Pendiente auditoría automática de vulnerabilidades: instalar pip-audit 2.10.1 en un entorno separado y ejecutar `python -m pip_audit -r requirements.txt --no-deps --disable-pip --format json`. No afirmar ausencia de vulnerabilidades sin resultado.
- Imágenes con versión explícita, sin `latest`: PostgreSQL 16.15 Alpine y Redpanda v26.2.2. Fuentes: [versiones PostgreSQL](https://www.postgresql.org/support/versioning/) y [release Redpanda](https://github.com/redpanda-data/redpanda/releases/tag/v26.2.2). Descarga y arranque pendientes de validación en Docker.

## Evidencia de esta sesión

- 10 pruebas unitarias/integración pasaron con Python 3.12.3 y PostgreSQL 17.8 aislado en `.local/pg-test`, puerto 55439. SQL aplicado dos veces; conexiones reales de los cuatro usuarios, restricciones administrativas, UPDATE de negocio sintético y protección de auditoría comprobados.
- Las seis pruebas unitarias también pasaron con Python optimizado (`-O`): la validación de credenciales no depende de instrucciones assert. El servidor de prueba se detuvo al terminar; no se dejaron servicios nuevos ejecutándose.

Docker no tiene motor accesible y su plugin no se descubre desde `docker compose` en este entorno; GNU Make no está disponible. `up` y `down` devolvieron errores, sin simular éxito.
